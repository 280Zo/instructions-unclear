## Evidence and reading guide

Sources are the October 15 PMB/Docling source audit, the October 16 technology survey, and an October 16 objective-by-objective research pass over papers, official documentation, source code and maintainer issue trackers. No products, models, conversions, retrieval quality, concurrency, authorization or deletion behavior were runtime-verified in this environment.

- **Documented:** primary project documentation describes the capability; this is not a passing workload test.
- **Source-inspected:** relevant implementation or package metadata was read; its version/snapshot limits apply.
- **Measured:** a paper or independent evaluation reports numbers for a stated dataset and setup. It does not predict results on this workload.
- **Vendor-measured:** the system's own authors measured it, often on private or self-selected data. Treat as a lead, not independent evidence.
- **Reported issue:** a user or maintainer issue documents observed behavior in a specific version; one report is anecdotal, not a defect rate.
- **Live metadata:** the earlier research read public GitHub repository API metadata directly, not a product runtime. Storage/ingestion observations were primarily at 07:58 UTC, with PMB at 07:56 and Weaviate at 08:02; memory-system observations were at 08:23–08:24 UTC on October 16, 2026.
- **Indexed metadata:** discovery-index snapshots only; archive status, release parity and current counts were not independently established.

Stars below are dated discovery metadata, not fit scores, production adoption or quality evidence. Push dates are activity signals, not reliability tests. Counts are not refreshed here or added across forks, connectors and composed stacks. GitHub availability includes BSL, SSPL, custom and non-OSI licenses; licenses, editions, model terms and cost remain deployment information, not an eligibility filter.

Capability references use the definitions in [01](01-objectives-and-requirements.md): **K1** durable cross-session memory/capture/maintenance; **K2** typed entities/facts/relations; **K3** documents/images/originals; **K4** accurate exact/vector/graph retrieval; **K5** shared project scope; **K6** provenance; **K7** updates/supersession/deletion/rebuild. A reference identifies relevant evidence, not full satisfaction of that capability.

## Findings by objective

This section summarizes what the evidence shows existing approaches can and cannot do. Design patterns these findings suggest considering are in [02](02-architecture-and-concepts.md#patterns-the-evidence-supports-evaluating); proposed tests are in [04](04-evaluation-and-experiments.md).

### K1 Capture, consolidation and maintenance

| Capture route | How it works | Evidence of trade-offs |
|---|---|---|
| Lifecycle hooks | Prompt, tool-use and session-end events go to a worker that compresses them into observations (claude-mem, agentmemory, MCP Memory Service) | Captures without agent cooperation wherever the hooks fire, but noisy: one audit labelled 23 of 49 claude-mem observations noise; another reported one prompt recorded 9 times and about 15.5k injected tokens at session start ([#1709](https://github.com/thedotmack/claude-mem/issues/1709), [#444](https://github.com/thedotmack/claude-mem/issues/444); reported issues) |
| Explicit agent writes | The agent calls a memory tool (PMB, Letta core-memory tools) | High signal and cheap, but depends on the agent writing and later reading. PMB's README names getting agents to use stored memory as the hard part ([README](https://github.com/oleksiijko/pmb); documented) |
| Transcript extraction | An LLM extracts facts from messages on each add (Mem0) or episode (Graphiti) | Retention depends on the extraction prompt and model |
| Asynchronous reflection | A separate agent consolidates memory while the main agent is idle (Letta sleep-time) | Keeps work off the request path; errors are harder to trace and it costs extra compute ([Letta](https://www.letta.com/blog/sleep-time-compute/); documented) |
| Evidence/inference separation | World facts, agent experience, observations and opinions kept in separate networks (Hindsight) | Keeps the provenance of inference clear at the cost of pipeline complexity ([paper](https://arxiv.org/abs/2512.12818); documented) |

Consolidation and update findings:

- **Destructive reconciliation loses information.** Mem0 describes its original extract-then-ADD/UPDATE/DELETE design as having destroyed context through overwrites and deletions. Current open-source Mem0 is add-only, defers "which fact is current" to retrieval, and lowered default `top_k` from 100 to 20 ([blog](https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm), [migration](https://docs.mem0.ai/migration/oss-v2-to-v3); vendor documented).
- **Invalidation instead of deletion** keeps history: Graphiti edges carry `valid_at`/`invalid_at` (world time) and `created_at`/`expired_at` (system time) ([facts](https://help.getzep.com/facts); documented).
- **Verbatim plus extracted keys outperforms either alone.** LongMemEval found round-level storage beats session-level storage; compressing to user facts loses information; using extracted facts as additional index keys over verbatim values raised recall@k 9.4% and QA accuracy 5.4%; time-aware query expansion raised temporal recall 6.8–11.3% ([paper](https://arxiv.org/abs/2410.10813); measured on a personal-chat corpus).
- **Linking and rewriting notes** (A-MEM) is a published design ([paper](https://doi.org/10.52202/085713-0593)); a follow-up reports its stored content quality is low ([MMS](https://arxiv.org/abs/2508.15294); measured).
- **Outcome-based quality:** later task outcomes can label stored memories for quality-based deletion, and bad retrieved records get copied into new records, propagating errors ([Xiong et al.](https://doi.org/10.18653/v1/2026.acl-long.27); measured).
- Decay/importance scoring and controlled forgetting exist in MCP Memory Service ([tests](https://github.com/doobidoo/mcp-memory-service/blob/0bbbd2e0/tests/consolidation/test_forgetting.py); source-inspected). A memory-operation taxonomy: consolidation, updating, indexing, forgetting, retrieval, compression ([survey](https://arxiv.org/abs/2505.00675); see also [ACM survey](https://doi.org/10.1145/3748302)).

Security and privacy findings:

- **Poisoning is effective at tiny rates.** AgentPoison reports at least 80% average attack success with under 0.1% of memory poisoned and at most 1% loss of normal performance ([paper](https://arxiv.org/abs/2407.12784); measured). MINJA describes injecting memories through queries alone, without store access ([paper](https://arxiv.org/abs/2503.03704); abstract-level). Forged-reasoning attacks are also reported ([preprint](https://arxiv.org/abs/2607.05029)).
- A-MemGuard reports over 95% attack-success reduction through consensus across related memories and a separate lesson store ([preprint](https://arxiv.org/abs/2510.02373); author-reported).
- MEXTRA extracts private stored queries from memory agents in a black-box setting ([paper](https://doi.org/10.18653/v1/2025.acl-long.1227); measured).
- For coding agents, every repository file, web page and tool output an agent reads is a potential memory-injection source.

### K2 Typed relationships and extraction reliability

| Approach | Relationship representation | Examples |
|---|---|---|
| Schema-constrained LLM extraction | Allowed entity/edge types, sometimes per entity pair; out-of-schema output dropped or annotated | Graphiti custom types with `edge_type_map` ([docs](https://help.getzep.com/graphiti/core-concepts/custom-entity-and-edge-types)); Cognee OWL grounding with annotate/strict modes and GLiNER2 custom labels ([ontology](https://docs.cognee.ai/guides/ontology-support), [GLiNER2](https://docs.cognee.ai/guides/gliner-llm-free-cognify)); KAG schema-constrained extraction with mutual graph–chunk indexing ([paper](https://arxiv.org/abs/2409.13731)) |
| Open/free-text extraction | Free-text relation descriptions or OpenIE triples without a predicate vocabulary | Microsoft GraphRAG ([methods](https://microsoft.github.io/graphrag/index/methods/)); LightRAG ([core docs](https://github.com/HKUDS/LightRAG/blob/main/docs/ProgramingWithCore.md)); HippoRAG 2 OpenIE plus synonym edges and Personalized PageRank ([paper](https://arxiv.org/abs/2502.14802)) |
| Shared-entity links | Memories connected because they mention the same entity | Current Mem0 Platform graph; open-source Mem0 v3 removed external graph stores ([graph memory](https://docs.mem0.ai/platform/features/graph-memory), [migration](https://docs.mem0.ai/migration/oss-v2-to-v3)). This is co-occurrence, not typed fact relationships |
| Authored relations | Agent or human writes typed relations in source files; a database is a secondary index | Basic Memory `- implements [[...]]` relations and categorized observations ([format](https://docs.basicmemory.com/raw/concepts/knowledge-format.md)) |
| Code-derived structure | Parser/compiler relations: defines, calls, imports, implements | SCIP/LSIF compiler-accurate references ([Sourcegraph](https://sourcegraph.com/docs/code-navigation/precise-code-navigation)); tree-sitter with heuristic resolution (codebase-memory-mcp, Aider repo map) |

Reliability evidence:

- **LLM triple extraction from prose is weak.** On DocRED with 6 entity and 96 relation types, entity F1 was 74–84% but triple F1 was 39.9% (Claude Opus 4.5), 39.3% (Gemini 3 Pro), 21.7% (GPT-5.1) and 4.2% (Mistral 7B); hallucinated and missed triples dominated. Only 10 documents with incomplete gold labels, so these are lower bounds ([Ilves et al.](https://aclanthology.org/2026.kallm-1.21.pdf); measured).
- **LLM-built GraphRAG graphs** captured only 68% of gold supporting sentences correctly with the strongest builder. Errors included over-generalized relations, attachment to co-mentioned entities, flipped direction, missing bridge edges and dropped qualifiers ([paper](https://arxiv.org/html/2603.14828v2); measured). Triple-extraction quality is the downstream bottleneck ([TACL](https://aclanthology.org/2026.tacl-1.29.pdf)).
- **Graph retrieval helps reasoning and hurts simple lookup.** Plain RAG was better on factual and detail questions; GraphRAG helped multi-hop reasoning; community/global GraphRAG generally underperformed on summarization against human references; LLM-judge verdicts flipped with presentation order ([Han et al.](https://doi.org/10.1145/3770855.3817575), [comparison](https://arxiv.org/abs/2502.11371); measured). GraphRAG-Bench reports basic RAG equal or better on simple fact retrieval ([paper](https://arxiv.org/html/2506.05690); measured).
- **Deterministic code structure is more reliable but not infallible.** codebase-memory-mcp records a confidence and resolution strategy per call edge, for example 0.85 for suffix matches ([source](https://github.com/DeusData/codebase-memory-mcp/blob/main/src/pipeline/pass_calls.c)); its own tests record near-zero IMPORTS edges for Rust, Kotlin, Java, C# and PHP repositories despite extracted imports ([test](https://github.com/DeusData/codebase-memory-mcp/blob/main/tests/test_edge_imports.c); source-inspected). Its paper reports 83% answer quality versus 92% for file exploration at about 10× fewer tokens ([paper](https://arxiv.org/abs/2603.27277); vendor-measured, author-graded).
- **Extraction cost is material.** Graphiti makes several LLM calls per episode for extraction, reflection, entity resolution, edge deduplication and invalidation ([paper](https://arxiv.org/abs/2501.13956); documented); LightRAG reports merge-phase embedding storms ([#1957](https://github.com/HKUDS/LightRAG/issues/1957); reported issue).

### K3 Documents, images and originals

- **Parsers preserve different anchors.** Docling's `DoclingDocument` holds typed items with page, bounding box and origin provenance; picture classification, picture description and chart extraction are opt-in enrichments, and pixels are retained only when page or picture image generation is enabled ([tech report](https://arxiv.org/html/2408.09869v4), [core types](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/document.py), [enrichments](https://docling-project.github.io/docling/usage/enrichments/)). MinerU outputs per-region position and order with named crop files ([outputs](https://opendatalab.github.io/MinerU/reference/output_files/)); Marker outputs a block tree with ids and polygons ([README](https://github.com/datalab-to/marker/blob/master/README.md)). None provides content-addressed original storage; that is an integration responsibility.
- **Page-image retrieval outperforms parsed text on visually rich pages.** On ViDoRe v1, ColPali scored 81.3 nDCG@5 versus 66.1 for OCR plus text embeddings and 67.0 with VLM captioning; generic SigLIP, Jina-CLIP and Nomic-vision scored 51.4, 17.7 and 12.9; indexing took 0.39 s versus 7.22 s per page ([ColPali](https://arxiv.org/html/2407.01449); measured). On ViDoRe V3 the best visual retriever scored 59.8 nDCG@10 versus 51.0 for the best text retriever on extracted Markdown and 20.3 for BM25; adding image descriptions to text did not help; fine-grained bounding-box grounding remains weak ([paper](https://arxiv.org/html/2601.08620); measured).
- **Counter-evidence:** an OCR pipeline with a strong VLM generalized better than ColPali to unseen and degraded documents ([Most et al.](https://doi.org/10.1145/3704268.3742698); measured).
- **Multi-vector storage cost:** ColPali stores about 1,030 vectors of 128 dimensions per page, roughly 257 KB in 16-bit float. Binary quantization costs a reported 52.4 to 49.5 nDCG@5, recoverable by float reranking ([Vespa](https://blog.vespa.ai/scaling-colpali-to-billions/); vendor-measured). Qdrant and LanceDB document multi-vector support ([Qdrant](https://qdrant.tech/documentation/tutorials-search-engineering/pdf-retrieval-at-scale/), [LanceDB](https://docs.lancedb.com/search/multivector-search)).
- **VLM interpretation fails on the facts agents act on.** CharXiv reasoning: GPT-4o 47.1%, best open model 29.2%, humans 80.5%; perturbed charts dropped scores up to 34.5% ([CharXiv](https://doi.org/10.48550/arxiv.2406.18521)). Qwen2.5-VL CharXiv reasoning falls from 49.7 (72B) to 42.5 (7B) and 31.3 (3B) while DocVQA stays above 93 ([report](https://arxiv.org/html/2502.13923)). BlindTest geometric tasks: frontier average 58.07% versus humans near 100% ([paper](https://doi.org/10.48550/arxiv.2407.06581)). Explicit arrow detection raised flowchart QA from 80% to 89% on a 90-question set ([paper](https://arxiv.org/abs/2505.07864)); edge direction emerges only in later model layers ([probe](http://arxiv.org/abs/2603.02865)). Engineering-diagram description Token-F1 was 0.03–0.18 ([ENGINUITY](https://arxiv.org/abs/2606.03410)). All measured.
- **Graphs built from image descriptions inherit description errors.** RAG-Anything links MLLM-described images, tables and equations as anchor nodes with `belongs_to` edges into a LightRAG graph ([paper](https://arxiv.org/html/2510.12323), [repo](https://github.com/HKUDS/RAG-Anything)); its reported gains are vendor-measured. MMORE unifies many media types into dense and sparse search ([repo](https://github.com/swiss-ai/mmore)).
- **Local model sizes:** SmolVLM-256M runs in under 1 GB GPU memory ([paper](https://arxiv.org/abs/2504.05299)); granite-docling has 258M parameters ([card](https://huggingface.co/ibm-granite/granite-docling-258M)); Qwen3-VL ships 2B–32B dense and MoE variants ([repo](https://github.com/QwenLM/Qwen3-VL/)); SigLIP2 covers 86M–1B image encoders ([paper](https://doi.org/10.48550/arxiv.2502.14786)). No official end-to-end VRAM table was found.

### K4 Retrieval accuracy by question type

- **Identifiers need lexical retrieval.** On EntityQuestions, DPR averaged 49.7% versus BM25's 71.2%, with gaps near 60 points on some patterns ([paper](https://doi.org/10.18653/v1/2021.emnlp-main.496); measured). BM25 remains a strong zero-shot baseline ([study](https://doi.org/10.48550/arxiv.2306.07471)).
- **Conceptual questions benefit from layered techniques.** Anthropic's contextual retrieval reduced top-20 failure from 5.7% to 3.7% with contextual embeddings, 2.9% adding contextual BM25 and 1.9% adding reranking ([engineering post](https://www.anthropic.com/engineering/contextual-retrieval); vendor-measured on internal data).
- **Routing beats one pipeline for every query.** Applying graph retrieval to all queries causes accuracy drops and latency ([EA-GraphRAG](https://arxiv.org/abs/2602.03578); measured); a learned router reported 2.5% higher accuracy and 12.4× speed over the best static pipeline ([RetrievalRouter](https://arxiv.org/abs/2608.25625); author-reported preprint).
- **Code-specific evidence is mixed.** Claude Code's team states agentic search outperformed RAG and that indexes went stale ([HN](https://news.ycombinator.com/item?id=43164253), [interview](https://newsletter.pragmaticengineer.com/p/building-claude-code-with-boris-cherny); claimed, no published evaluation). Cursor reports 12.5% higher QA accuracy from adding semantic search to grep ([blog](https://cursor.com/blog/semsearch); vendor-measured, private benchmark). An independent study found grep generally beat vector search across agent harnesses, with results depending on harness and how tool results were delivered ([paper](https://arxiv.org/abs/2605.15184); measured, chat-history corpus rather than code). Sourcegraph moved away from embeddings for operational reasons ([blog](https://sourcegraph.com/blog/how-cody-understands-your-codebase)). AST-derived repository graphs improved SWE-bench systems ([RepoGraph](https://arxiv.org/abs/2410.14684); measured, gain sizes not verified here); hierarchical localization reached 32% on SWE-bench Lite ([Agentless](https://arxiv.org/abs/2407.01489); measured); code retrieval remains hard for strong retrievers ([CoIR](https://arxiv.org/abs/2407.02883), [CodeRAG-Bench](https://doi.org/10.48550/arxiv.2406.14497)); all measured. Index staleness is reported as a major cost of embedding code by Claude Code (claimed) and Sourcegraph (operational), but no measurement of its accuracy impact was found.
- **Public memory benchmarks do not cover this workload.** LongMemEval tests extraction, multi-session and temporal reasoning, knowledge updates and abstention on personal chat ([paper](https://arxiv.org/abs/2410.10813)); MemoryAgentBench adds selective forgetting ([paper](https://arxiv.org/abs/2507.05257)); BEAM stresses scale ([paper](https://arxiv.org/abs/2510.27246)). A third-party audit found 6.4% of LoCoMo answers corrupt ([audit](https://github.com/dial481/locomo-audit/blob/main/AUDIT_REPORT.md); independent, not peer-reviewed); Zep and Mem0 dispute each other's LoCoMo numbers ([issue](https://github.com/getzep/zep-papers/issues/5), [Zep response](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/); vendor-measured on both sides); changing only the reader model or re-ask budget moved scores 2.0–8.9 points ([paper](https://arxiv.org/abs/2608.23920); vendor-measured, single author). A Letta filesystem agent with grep reported 74.0% on LoCoMo ([blog](https://www.letta.com/blog/benchmarking-ai-agent-memory/); vendor-measured). None tests code identifiers or dependency traversal.
- **Evaluation methods with evidence:** claim-decomposition faithfulness ([RAGAS](https://doi.org/10.18653/v1/2024.eacl-demo.16)), judge-bias correction with a small human-labelled set ([ARES](https://doi.org/10.18653/v1/2024.naacl-long.20)), and unanswerable-question categories, where no configuration was best at both abstaining and answering ([UAEval4RAG](https://doi.org/10.18653/v1/2025.acl-long.415)).

### K5 Host integration, sharing and isolation

OpenCode V2 (documented, from V2 docs only):

- **One user-level background service** owns sessions, configuration, integrations, permissions and tool execution for every local client; `--standalone` runs a private server ([CLI](https://opencode.ai/v2/docs/cli/)). Sessions live in one database ([troubleshooting](https://opencode.ai/v2/docs/troubleshooting/)).
- **Plugins receive a location** (`directory`, optional `workspaceID`, `project`). The docs warn this is the plugin instance's location, not that of every session or event it can access; external event streams span locations ([plugins](https://opencode.ai/v2/docs/build/plugins/), [RPC](https://opencode.ai/v2/docs/build/plugins/rpc/)). `ctx.storage` is durable plugin-scoped JSON; its location scope is not documented.
- **Capture hooks:** session `prompt`, `context` (before every model call), `compaction` (can supply or replace the summary), `generate` and `title`; tool `execute.before` and `execute.after`; event subscription. Hook changes affect the outgoing call, not persisted history.
- **Injection paths:** `context`-hook system additions, synthetic session messages, API-managed session instruction entries (position 6 in prompt assembly), MCP server instructions (position 3), and skill/reference transforms ([instructions](https://opencode.ai/v2/docs/instructions/), [API](https://opencode.ai/v2/docs/api/)). `AGENTS.md`, `instructions` and `references` provide file-based persistent context; no built-in memory store is documented ([references](https://opencode.ai/v2/docs/references/)).
- **Subagents run in child sessions** with fresh context, filterable by `parentID`; whether session hooks fire for child sessions is not documented ([agents](https://opencode.ai/v2/docs/agents/), [tools](https://opencode.ai/v2/docs/tools/)).
- **MCP tool calls carry** `_meta["ai.opencode/sessionID"]`, which the docs say must not be used alone for authentication ([MCP](https://opencode.ai/v2/docs/mcp-servers/)).
- **Tested here on OpenCode v2.0.29 (E13, [04](04-evaluation-and-experiments.md#experiment-record-template)):** prompt, context, tool and compaction hooks fired; context-hook system additions and prompt-hook edits reached the model in parent and subagent sessions; subagent creation ran the prompt and context hooks in the child session; event subscription delivered events. A beta report of event subscription and `context`-hook changes not reaching the model ([#44788](https://github.com/anomalyco/opencode/issues/44788), related [#43731](https://github.com/anomalyco/opencode/issues/43731)) did not reproduce on this build. agentmemory marks its V2 compaction hook unverified ([plugin](https://github.com/rohitg00/agentmemory/blob/main/plugin/opencode/README.md)); the hook fired here.

Concurrency and local-service findings:

- SQLite with `busy_timeout=0` silently dropped claude-mem observations ([#2821](https://github.com/thedotmack/claude-mem/issues/2821)); one MCP process per session over SQLite caused lock crashes and orphaned processes, fixed with longer timeouts, backoff and cleanup ([context-mode #218](https://github.com/mksglu/context-mode/issues/218)); another project opened its MCP database read-only to stop multi-session hangs ([commit](https://github.com/webgress/msgvault/commit/9920d14fbc55d7b37b3ac2548deaa191ec603d6d)). Reported issues.
- Embedded Chroma is not process-safe for concurrent writers ([constraints](https://cookbook.chromadb.dev/core/system_constraints/)); Kuzu-lineage engines allow one read-write database object ([Kuzu](https://kuzudb.github.io/docs/concurrency/)); LanceDB uses optimistic concurrency where many writers can fail commits ([FAQ](https://docs.lancedb.com/faq/faq-oss), [transactions](https://lance.org/format/table/transaction/)). Documented.
- Daemon patterns avoid multi-writer files. agentmemory runs a local server plus an MCP shim; MCP Memory Service runs a local HTTP service, documents sqlite-vec as single-user, and its OpenCode quickstart enables anonymous access ([repo](http://github.com/doobidoo/mcp-memory-service), [FAQ](https://codeberg.org/doobidoo/mcp-memory-service/wiki/08-FAQ.md)).
- Official MCP Python and TypeScript SDKs shipped localhost HTTP servers without DNS-rebinding protection, fixed in 1.23.0 and 1.24.0 ([Python](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-9h52-p55h-vw2f), [TypeScript](https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-w48q-cv73-mx4w)). MCP guidance for local servers is stdio, an auth token, or Unix sockets/IPC ([best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)).

### Project separation research

**Database tenancy models** (primary guidance; vendor opinions marked):

- Three standard models: shared tables with a tenant column ("pool"), schema or namespace per tenant ("bridge"), and database per tenant ("silo") ([AWS whitepaper](https://docs.aws.amazon.com/pdfs/whitepapers/latest/saas-tenant-isolation-strategies/saas-tenant-isolation-strategies.pdf), [AWS RLS blog](https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/), [Azure SQL patterns](https://learn.microsoft.com/en-us/azure/azure-sql/database/saas-tenancy-app-design-patterns), [Azure storage approaches](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data); documented).
- Azure rates database-per-tenant isolation highest and names restoring one tenant from a shared database as a hard case (documented). Citus suggests a database per tenant is maintainable at "5 or 50 tenants" and shared tables at thousands ([Citus](https://www.citusdata.com/blog/2016/10/03/designing-your-saas-database-for-high-scalability/); vendor guidance). Neon advises against schema-per-tenant unless experienced with it ([Neon](https://neon.com/docs/guides/multitenancy); vendor opinion). Postgres has no hard schema limit ([Stack Overflow](https://stackoverflow.com/questions/14893964/how-many-schemas-can-be-created-in-postgres); practitioner answers), but many schemas slow `pg_dump` and tools ([pgsql list](https://www.postgresql.org/message-id/20190604201835.GV2480%40tamriel.snowman.net)).
- **Filter failures:** a misnested `OR` negated an account filter and exposed other accounts for about two hours ([Checkly post-mortem](https://www.checklyhq.com/blog/post-mortem-security-incident/)); missing row-level security exposed whole tables ([CVE-2025-48757 statement](https://mattpalmer.io/posts/2025/05/statement-on-CVE-2025-48757/)). Postgres row-level security is bypassed by superusers, `BYPASSRLS` roles and table owners unless forced ([docs](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)); common mistakes are listed by [Bytebase](https://www.bytebase.com/blog/postgres-row-level-security-footguns/) (vendor blog).
- SQLite has no schemas; attached databases default to a limit of 10, maximum 125 ([limits](https://www.sqlite.org/limits.html); documented). Turso and Cloudflare Durable Objects use a SQLite database per tenant ([Turso](https://turso.tech/blog/multi-tenancy-at-scale), [Durable Objects](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/); vendor documentation).

**Namespaces as a security boundary** (documented):

- Kubernetes: a namespace isolates API resources, but "the namespace isolation model requires configuration of several other Kubernetes resources"; RBAC roles and network policies are scoped to namespaces to restrict access ([multi-tenancy](https://kubernetes.io/docs/concepts/security/multi-tenancy/)).
- AWS: an account is an isolation boundary with no cross-account access by default; separating production from non-production accounts is a stated design principle ([multi-account whitepaper](https://docs.aws.amazon.com/pdfs/whitepapers/latest/organizing-your-aws-environment/organizing-your-aws-environment.pdf)).
- SurrealDB: system users can be defined on root, namespace or database level, with OWNER, EDITOR or VIEWER roles ([DEFINE USER](https://surrealdb.com/docs/reference/query-language/statements/define/user)).
- Postgres: by default users cannot access objects in schemas they do not own unless granted `USAGE`; the docs describe secure schema-usage patterns ([schemas](https://www.postgresql.org/docs/current/ddl-schemas.html)).

### K6 and K7 Provenance, supersession and deletion

- **Provenance lists, not single creators.** Graphiti edges list supporting episode IDs ([source](https://github.com/getzep/graphiti/blob/main/graphiti_core/edges.py)); LightRAG keeps a `source_id` chunk chain ([docs](https://github.com/HKUDS/LightRAG/blob/main/docs/ProgramingWithCore.md)); GraphRAG claims with status, dates and source text exist but are off by default ([outputs](https://microsoft.github.io/graphrag/index/outputs/)).
- **Documented deletion semantics diverge from code.** Zep describes removing a fact only when no remaining episode supports it ([blog](https://blog.getzep.com/how-zep-tracks-provenance-in-agent-memory/)). Graphiti's `remove_episode` on main deletes edges whose first supporting episode is removed, even if later episodes confirmed them ([source](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/graphiti.py)), and the MCP delete tool did not cascade ([#1491](https://github.com/getzep/graphiti/issues/1491)). Mem0's paper describes marking graph edges invalid while its graph-store code, before v3 removed external graph stores, hard-deleted them ([#4187](https://github.com/mem0ai/mem0/issues/4187)). Source-inspected and reported.
- **Rebuild cost after deletion.** LightRAG rebuilds shared entities from remaining chunks with the LLM; deleting 85 documents caused about 75× redundant LLM calls, and partial deletes needed retry-safety fixes ([#2795](https://github.com/HKUDS/LightRAG/issues/2795), [PR #2826](https://github.com/HKUDS/LightRAG/pull/2826); reported).
- Deleting a Basic Memory file deletes its knowledge, with history depending on Git. Cognee does not reload a changed ontology while running ([ontology](https://docs.cognee.ai/guides/ontology-support)).

### What the evidence leaves open

No public evaluation measures this workload end to end: code identifiers, dependency traversal, typed relationships from project documents, diagram and photo facts, superseded decisions, and project isolation for OpenCode sessions and subagents. Leading memory benchmarks are disputed or vendor-run. Fusion method, local reranker effects on identifiers, re-indexing cost versus always-fresh grep, and whether OpenCode V2 hooks deliver captured and injected context in the current build remain unmeasured. These gaps define the experiments in [04](04-evaluation-and-experiments.md).

### Combining keyword, vector and relationship search

- **Fusion:** a weighted score combination beat Reciprocal Rank Fusion (RRF) in and out of domain and can be tuned from a few labelled queries; RRF discards score gaps, so a strong exact match counts like a weak one ([Bruch et al.](https://arxiv.org/abs/2210.11934); measured). Defaults: LanceDB RRF k=60 ([docs](https://docs.lancedb.com/reranking/rrf)), Elastic RRF 60 ([docs](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/retrievers/rrf-retriever)), Qdrant RRF or z-score fusion ([docs](https://qdrant.tech/documentation/search/hybrid-queries/)), Weaviate min-max with alpha 0.75 ([docs](https://docs.weaviate.io/weaviate/concepts/search/hybrid-search)).
- **Keyword search for code:** GitHub and Zoekt use trigram indexes plus symbol and word-boundary signals ([GitHub](https://github.blog/engineering/architecture-optimization/the-technology-behind-githubs-new-code-search/), [Zoekt](https://github.com/sourcegraph/zoekt/blob/main/doc/design.md)). Sourcegraph reports about 20% better code search from field-weighted BM25 with filename and symbol matches weighted 5× ([blog](https://sourcegraph.com/blog/keeping-it-boring-and-relevant-with-bm25f); vendor-measured). SQLite FTS5 offers `unicode61` with `tokenchars`, `porter` (stemming, wrong for identifiers) and `trigram` ([docs](https://sqlite.org/fts5.html)); Tantivy supports n-gram and custom tokenizers ([example](https://tantivy-search.github.io/examples/custom_tokenizer.html)). No study isolating identifier splitting was found.
- **Rerankers:** on code, Qwen3-Reranker scored 73.4 (0.6B) and 81.2 (4B) against 41.4 for bge-reranker-v2-m3 ([paper](https://arxiv.org/abs/2506.05176)); jina-reranker-v3 scored 70.6 on CoIR against 36.3 for bge-v2-m3 ([card](https://huggingface.co/jinaai/jina-reranker-v3)); mxbai-rerank-v2 BEIR 55.6–57.5 ([card](https://huggingface.co/mixedbread-ai/mxbai-rerank-large-v2)). All vendor-measured. Reranker benefit shrinks and can turn negative as rerank depth grows ([Jacob et al.](https://arxiv.org/abs/2411.11767); measured); one study found cross-encoders lowered answer quality while an LLM reranker helped ([paper](https://link.springer.com/article/10.1007/s10791-026-10156-3)). No evidence was found on whether rerankers demote exact identifier matches.
- **Chunking:** AST-based code chunking improved Recall@5 by 4.3 and SWE-bench Pass@1 by 2.67 over line-based chunking ([cAST](https://doi.org/10.18653/v1/2025.findings-emnlp.430); measured). Small chunks (64–128 tokens) suit short facts, large (512–1024) suit context-heavy questions ([paper](https://arxiv.org/abs/2505.21700)); semantic chunking did not justify its cost ([paper](https://doi.org/10.18653/v1/2025.findings-naacl.114)). Late chunking added about 1.5–1.9 nDCG@10 ([paper](https://arxiv.org/html/2409.04701v2)). Docling's HybridChunker splits by document structure and adds heading paths ([docs](https://docling-project.github.io/docling/concepts/chunking/)).
- **Relationship expansion and routing:** earlier graph systems fell below plain search on simple facts; HippoRAG 2 recovered this and added 7% on associative tasks ([paper](https://arxiv.org/abs/2502.14802); measured). LightRAG's gains rest mostly on LLM judging ([paper](https://doi.org/10.18653/v1/2025.findings-emnlp.568)). Graphiti ships fusion and graph-distance search recipes ([source](https://github.com/getzep/graphiti/blob/main/graphiti_core/search/search_config_recipes.py)). A small classifier choosing the retrieval strategy improved accuracy and efficiency ([Adaptive-RAG](https://doi.org/10.18653/v1/2024.naacl-long.389); measured).
- **Query side:** LongMemEval's gains from per-round storage, fact-expanded keys and time-aware filtering apply (see K1). HyDE helps untrained dense retrievers ([paper](https://doi.org/10.18653/v1/2023.acl-long.99)) and is likely unhelpful for identifiers. No primary evidence on recency boosts was found.
- **Delivering results:** Anthropic recommends returning compact identifiers and letting the agent fetch details ([guidance](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)); passing 20 chunks beat 10 or 5 in its contextual retrieval tests.

## Documents and images: ingestion on the target hardware

Researched October 16, 2026. Scores are vendor-reported unless marked.

### Documents through Docling

- **Versions:** Docling v2.135.0 and docling-mcp v3.3.0 (October 2026); docling-mcp added picture-description options and a bounded, content-keyed conversion cache, not a durable store ([changelog](https://github.com/docling-project/docling/blob/main/CHANGELOG.md), [docling-mcp releases](https://github.com/docling-project/docling-mcp/releases)).
- **Provenance:** each chunk keeps page number, bounding box and a `self_ref` path; each document keeps a 64-bit `binary_hash`, filename and type ([LangChain loader](https://docs.langchain.com/oss/python/integrations/document_loaders/docling), [document schema](https://github.com/docling-project/docling-core/blob/main/docs/DoclingDocument.json)). Figures and tables can be re-cropped when image generation is on ([export figures](https://docling-project.github.io/docling/_generated/examples/export_figures/)).
- **Options:** TableFormer fast and accurate modes ([advanced options](https://docling-project.github.io/docling/usage/advanced_options/)); OCR engines RapidOCR (defaults to Chinese, set the language), EasyOCR, Tesseract, Nemotron-OCR ([OCR](https://docling-project.github.io/docling/concepts/OCR/)); picture classification, description and chart extraction are opt-in ([enrichments](https://docling-project.github.io/docling/usage/enrichments/), [chart extraction](https://github.com/docling-project/docling/blob/main/docs/examples/chart_extraction.py)); HybridChunker repeats table headers and adds heading paths ([chunking](https://docling-project.github.io/docling/concepts/chunking/)).
- **Speed:** without OCR, 4.2 pages/s on an RTX 5070 and 7.9 on an RTX 5090; with OCR about 1.1–1.6 pages/s; CPU only about 1.2–1.5 pages/s ([GPU guide](https://docling-project.github.io/docling/usage/gpu/); vendor-measured). The target GPU is expected between the two (estimate).
- **Local picture description:** built-in SmolVLM and granite-vision presets, any Hugging Face model, or a local OpenAI-compatible endpoint such as Ollama or vLLM ([API example](https://docling-project.github.io/docling/_generated/examples/pictures_description_api/)). No measured description quality was found.
- **Weak spots for datasheets and schematics (reported issues):** tables spanning pages are split ([#2976](https://github.com/docling-project/docling/issues/2976)); merged cells were wrong in every mode tested ([#3698](https://github.com/docling-project/docling/issues/3698)); a drawing detected as one full-page picture produced zero chunks without warning ([#3845](https://github.com/docling-project/docling/issues/3845)); the VLM pipeline fabricated paragraphs in one report ([#2444](https://github.com/docling-project/docling/issues/2444)). Schematic connectivity is not extracted; a schematic becomes a picture plus OCR text.
- **Memory products lose provenance:** Hindsight stores extracted facts, not original text, and re-extracts on re-upload ([retain](https://hindsight.vectorize.io/developer/api/retain)); Cognee's Docling loader keeps only plain text ([loaders](https://docs.cognee.ai/core-concepts/further-concepts/loaders)); LlamaIndex's Docling parser gives random node IDs unless configured ([parser](https://developers.llamaindex.ai/python/framework-api-reference/node_parser/docling/)). Hash-based skip of unchanged files exists in LlamaIndex's ingestion pipeline ([pipeline](https://developers.llamaindex.ai/python/framework/module_guides/loading/ingestion_pipeline/)).

**Vision models have distinct jobs.** OCR/parser output supplies text/layout; a VLM supplies descriptions or answers; an image/text encoder supplies comparable vectors for visual/text similarity. Text embeddings over captions are not direct image-vector indexing. Keyless BM25, provisioned small local encoders and generative-model processing are different routes, not one universal API requirement. No end-to-end privacy or LLM-provider constraint is assumed here; deployment policy remains a decision for [05](05-decisions-and-open-questions.md).

## 5. Cross-layer interpretation

Traceability differs by representation: MemPalace conversations, claude-mem timelines, Graphiti episodes and Hindsight source associations help K6, but do not establish retained original media, page bounding boxes or exact source-version retirement. Cognee/OpenViking corpus paths, Supermemory media support and MIRIX visual capture are relevant K3 candidates, not demonstrated arbitrary-photo accuracy or direct visual-similarity results.

K5 also has two boundaries: shared service/project routing versus credential-enforced access. Tags, wings/rooms, banks, datasets and `group_id` are not interchangeable ACLs. OpenViking/Cognee document authenticated options; Hindsight's default MCP and MCP Memory Service's default tagging merit particular qualification, without certifying other products secure or insecure.

Central storage outside checkouts can keep project content out of Git, but original files may still need filesystem/object storage beside indexes. Embedded stores need a serving/identity layer for central clients. Removing a checkout then does not remove central knowledge; K7 export, deletion, backups and rebuild become service operations. No physical layout is selected here.

Accepted asynchronous writes may not yet be searchable. Shared backend storage does not demonstrate distinct host session IDs, correct subagent capture, immediate visibility, cross-store atomicity or absence of cache/outbox races. Temporal invalidation is not proof of deletion from originals, exports and backups. Source-linked extracted relations remain interpretations until supported/confirmed. Evaluation belongs in [04](04-evaluation-and-experiments.md), not feature checkmarks.
