# Reverse engineering

Three agents and four skills from Seth Hobson's agent collection, for binary, firmware and malware analysis.

- Agents: `reverse-engineer`, `firmware-analyst`, `malware-analyst`
- Skills: `binary-analysis-patterns`, `anti-reversing-techniques`, `memory-forensics`, `protocol-reverse-engineering`

From this repo it's a **profile**: it installs into one folder you choose, not your home folder. It pairs well with the [REA profile](../../mcp-servers/rea/) in the same folder.

## Install

From the repo root:

```bash
mkdir -p ~/reverse_engineering/re
npx rulesync@38.0.0 generate --config agents/reverse-engineering/profile.jsonc --output-roots ~/reverse_engineering/re --targets opencode,claudecode,codexcli
```

Swap `--targets` for your tools. Never add `--global`. Run the same command again to update.

## Tools you need

The profile installs instructions only. Choose tools for the artifact you are
authorized to examine; you do not need everything below for every task.

| Work | Tools and prerequisites |
| --- | --- |
| Static binary analysis | A disassembler/decompiler such as Ghidra, radare2, IDA Pro or Binary Ninja. Ghidra also needs the Java version required by its release; commercial tools need their own licenses |
| Debugging | GDB or LLDB on supported systems; x64dbg for Windows. Attach permissions and target access are separate from this profile |
| Memory forensics | Volatility 3, Python and suitable OS symbols; an already-acquired memory image. Memory acquisition tools/drivers are a separate privileged setup |
| Protocol analysis | Wireshark or TShark and an authorized capture file. Live capture needs separate interface permissions and scope approval |
| Firmware | Binwalk or other chosen unpackers plus their extraction dependencies; architecture-specific tools as needed |
| Advanced analysis | Optional angr, Unicorn, Frida or QEMU when the selected workflow calls for them; use an isolated environment and their supported versions |

Install only the tools needed, following the approved procedure below. Installing
an analysis CLI does not install capture drivers, symbols or grant target access.
The [REA setup](../../mcp-servers/rea/#install) has its own runtime/backend
requirements if you also want its MCP integration. Nothing here runs tools or
analyzes an artifact merely by being installed.

The [tooling assessment](../../reference/security-re-tooling.md) covers the full categorized inventory, AI interfaces and overlap with these agents. The [reverse-engineering group](../../groups/README.md#reverse_engineering) also includes REA and ReVa skills plus disabled ReVa/radare2 connections; this agent-only profile does not install those extras. IoTHackBot is now a separately installed native plugin, not generated by either profile.

## For agents: installing and verifying backends

Start in this repo and ask:

> Follow `agents/reverse-engineering/README.md` to prepare the tools for my chosen workflow. Inspect what is installed, propose the smallest setup, ask before changes, and verify it with harmless local fixtures. Do not analyze real targets.

This is a repo-owned setup procedure, not an upstream agent prompt. Keep it separate from the copied skills. Also follow the component-specific instructions for [REA](../../mcp-servers/rea/README.md#for-agents-install-and-verify), [ReVa](../../mcp-servers/reva/README.md#for-agents-install-and-verify) or [radare2 MCP](../../mcp-servers/radare2/README.md#for-agents-install-and-verify) when applicable.

### Approval before installation

1. Ask which workflow, OS/architecture, destination and assistant the user wants. Establish whether installation alone or fixture-based testing is authorized. Do not treat this request as permission to run a supplied binary, attach to a process, access a device, scan a host or capture traffic.
2. Inspect only the selected tools: existing executables and versions, project package/lock files, Java/Python requirements, and the selected component's configuration. Prefer an existing compatible installation. Do not dump the environment, read credentials, or run an installer merely to discover what is installed.
3. Read the selected tool's official installation instructions and the component's recorded version requirements. Follow links from its official project or vendor. Choose the smallest compatible toolset; do not install every item in the table. Check that the instructions apply to the released package, OS and architecture, not only an unreleased repository main branch. If no compatible build exists, stop and explain the choices rather than changing pins silently.
4. Show the exact proposed commands, versions, download origins, paths and expected side effects. Include dependencies, any compilation, package scripts, PATH/environment edits, disk needs, licenses and persistent services. Obtain approval before downloads or execution, OS/global installs, privileges, config edits, license acceptance, device permissions or enabling a disabled MCP connection. The user handles credentials and commercial activation.
5. Use the repository's package-management guidance when available. Prefer project-local or isolated environments and frozen dependency installs where supported. An approved user/system installation is a separate choice, not the default. Pin one-off runners to an exact reviewed release; do not add `--yes` or use `latest` to bypass review. This repo's existing launch definitions may already download packages at startup; include that in the approval. Never pipe downloads to a shell or disable signature, checksum, certificate, sandbox or permission checks.
6. Download only from official distributions or the approved OS registry. Verify publisher signatures/checksums when supplied; record the release and digest. If the expected verification fails, stop. If no independent publisher verification is available, disclose that before execution; a digest you compute yourself records identity but does not prove authenticity. Follow the supported installer; inspect its documented options and preview its changes when possible. Do not extract installer-owned integrations or create a second owner for existing skills/agents.
7. Back up only the approved files before changing them, keeping private settings outside this public repo. Make narrowly scoped changes; never overwrite the whole shell startup file or replace a working Java/Python installation to satisfy one tool. Prefer a session-local environment variable for a test. Persistent environment edits, service startup and host restarts need their own approval. If an interactive or privileged step cannot be performed, give it to the user and wait.

### Verification without operating a target

Installation, discovery and successful use are separate checks. Keep verification in an approved disposable workspace, with a list of everything it creates. Use documentation for the installed release to choose version/help and diagnostic commands; do not invent flags or treat a successful package install as a functional test.

| Selected workflow | Harmless smoke test and acceptance evidence |
|---|---|
| Ghidra, IDA, Hopper, Binary Ninja, radare2 or Rizin | Confirm the installed release and required runtime/license. With separate fixture approval, statically inspect a tiny local program compiled from recorded source and identify a known symbol or string. Approve any compiler installation separately. Do not execute the fixture or use a real application as the test |
| GDB, LLDB or x64dbg | Check startup/version without a target. If debugging functionality is requested, separately approve a self-authored fixture and its execution; never attach to an unrelated process. Report untested debugging as untested |
| Volatility 3 | Confirm CLI startup and discovery of the intended plugin, with no acquisition driver. Full analysis needs an explicitly approved test image and matching symbols; record it as untested if none is available |
| Wireshark/TShark | Confirm CLI or GUI startup without capture. With fixture approval, parse a small synthetic saved capture and verify a known packet/field. Do not start live capture, change capture groups or grant capabilities |
| Binwalk or other firmware unpackers | Check startup; inspect a synthetic local archive/image. Extraction needs separate approval, a new output directory and the tool's documented isolation controls. Do not extract untrusted firmware as a smoke test |
| angr, Unicorn, Frida or QEMU | Verify the chosen package's import/startup in its isolated environment. Any emulation, instrumentation, guest boot or device access requires an explicitly approved self-authored fixture and test command. Keep network and production targets out of the test |

For an MCP integration, first verify its configured executable/endpoint and catalog, then perform the approved fixture operation through the connected assistant. A connected MCP server does not prove its native backend works. Do not weaken host permissions or expose a listener beyond loopback to make the check pass.

### Handoff and rollback

Report each chosen tool as **present**, **installed**, **version verified**, **fixture verified**, **blocked** or **not tested**, with the command/result supporting that status. Include package versions, official sources, installation paths, changed config keys, remaining dependencies and approved test evidence. Redact private values. Do not label an entire profile working because one server connects.

Provide the supported uninstall/rollback procedure and the exact files/environments created by this run. Do not remove existing tools, shared caches, saved projects or forensic data. Stop only processes started for this test after checking their identity. Ask before rollback that replaces settings, uninstalls packages or deletes files, and preserve logs needed to explain a failed check.

- "Use `protocol-reverse-engineering` on the capture in `~/captures/device.pcap`"
